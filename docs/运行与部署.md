## 1. 运行结构

本版运行一个 Go 管理实例、一个 worker、PostgreSQL 16 和 Caddy 2.11.7。Go 提供前端构建文件和 API；Caddy 直接读取不可变发布目录。Go 或数据库短暂离线时，已有正式内容可继续由 Caddy 提供；预览鉴权依赖 Go 和数据库，依赖不可用时拒绝内容访问。

| 服务 | 数据和权限 | 对外端口 |
|---|---|---|
| app | 数据库、完整产物卷、网关管理 API；启动读取凭据后降为 UID 10001 | 回环 `18180` |
| worker | 只挂载上传子目录；独立内网，独立服务密钥，无数据库连接或正式内容卷 | 无 |
| caddy | 正式产物只读、配置持久化卷；以 UID 10001 运行 | 回环 `18080` |
| db | PostgreSQL 持久化卷，独立数据库内网 | 无 |
| init-data | 初始化目录所有者后退出 | 无 |

worker 在独立子进程中解包、检查；子进程清空环境且有执行时限。Compose 进一步限制内存、CPU、进程数和可写挂载。上传内容不在服务器执行，浏览器浏览公开页面时仍会执行页面自身脚本。原生 `scripts/dev.py` 便于开发，不具有容器挂载和网络隔离。

Caddy 的管理端口 `2019` 与探测端口 `8081` 未发布到宿主机端口；同一 `gateway` 网络的容器仍可访问它们，原生 Linux 宿主机通常也能直接访问容器 IP。Docker Desktop 的宿主机访问路径不同。管理 API 和探测监听依赖受信任的私有网络，不应向公网转发；网关保存配置中包含内部鉴权材料，配置卷和备份均应按敏感数据保护。

`internal: true` 不能隔离同网络容器或宿主机。app 当前通过 `gateway` 网络访问远端备份仓库；直接将其设为 internal 会去掉 app 的现有外网出口。调整网络边界时，须同时设计管理/探测访问限制与 app 的备份出口，并验证实际仓库连接。

## 2. 配置和初始化

```bash
python3 scripts/init-secrets.py
cp .env.example .env
docker compose up -d --build
```

初始化脚本只创建缺失的随机凭据，已有文件不被覆盖。`.secrets` 目录为 `0700`，凭据为 `0600`；数据库密码、内部鉴权密钥、worker 密钥、初始化凭据与备份口令分别保存。

在后台完成首次管理员设置。初始化接口在数据库已有管理员后拒绝再次设置。管理员会话最长 12 小时，30 分钟无 API 活动后失效。生产 Cookie 使用 `__Host-`、Secure、HttpOnly、Path=/，不设置 Domain；Cookie 写请求同时校验准确 Origin 和 CSRF Token。

| 配置 | 本地默认 | 说明 |
|---|---|---|
| `DROP_ADMIN_ORIGIN` | `http://localhost:18180` | 必须等于浏览器管理入口，不含末尾 `/` |
| `DROP_CONTENT_DOMAIN` | `drop.localhost:18080` | 正式和预览内容的 DNS 后缀 |
| `DROP_DEVELOPMENT_MODE` | `true` | 仅允许回环或 `.localhost`；公网必须 `false` |
| `DROP_TRUSTED_PROXY_CIDRS` | 空 | 逗号分隔的可信入口对端 IP/CIDR；为空时忽略 X-Forwarded-For |
| `DROP_ADMIN_PORT` | `18180` | 宿主机管理回环端口 |
| `DROP_CONTENT_PORT` | `18080` | 宿主机内容回环端口 |
| `DROP_QUOTA_BYTES` | `21474836480` | 20 GiB 应用配额 |
| `DROP_DISK_RESERVE_BYTES` | `5368709120` | 至少保留 5 GiB，另受磁盘 10% 门槛限制 |
| `RESTIC_REPOSITORY` | 空 | 未配置时界面显示未配置备份 |
| `DROP_SECRETS_DIR` | `.secrets` | Compose secret 文件目录 |

上传默认上限 200 MiB；单文件 100 MiB；解包后 1 GiB；最多 10,000 个文件；目录最多 20 层。Go 同时执行两个后台任务。服务端原生环境还可通过 `DROP_MAX_UPLOAD_BYTES`、`DROP_MAX_FILE_BYTES`、`DROP_MAX_EXPANDED_BYTES`、`DROP_MAX_FILES` 调整；调整前端提示和生产资源预算后再暴露相应 Compose 环境。

Compose 资源上限合计约 2 GiB，宿主机还需操作系统、Docker 和临时磁盘空间。建议先在至少 4 GiB 内存的目标环境压测；这属于部署建议，并非已验证的吞吐承诺。上传预占包含压缩文件和两份最大展开空间，小文件也先按最坏情况预留，避免并发超额。

## 3. douyacn.com 接入

正式 `.env` 至少设置：

```dotenv
DROP_ADMIN_ORIGIN=https://drop-admin.douyacn.com
DROP_CONTENT_DOMAIN=drop.douyacn.com
DROP_DEVELOPMENT_MODE=false
```

现有 HTTPS 入口需配置两个独立目的地：

| 域名 | 上游 | 必须保持 |
|---|---|---|
| `drop-admin.douyacn.com` | `127.0.0.1:18180` | 原 Host、Origin、Cookie、CSRF 头 |
| `*.drop.douyacn.com` | `127.0.0.1:18080` | 原 Host、路径、Cookie、Range、条件请求头 |

通配证书应覆盖 `*.drop.douyacn.com`；后台域名另行覆盖。DNS 与证书由既有入口管理，Compose 自身不占用 80/443，也不申请证书。内部 Caddy 明确关闭自动 HTTPS。

必须验证：

1. 管理入口仅路由到 Go；任意内容域名不会落入后台；未知 Host 返回 404。
2. 入口保留浏览器原始 Origin；不要把任意外部 Origin 重写为后台 Origin。
3. 上传请求体限制至少覆盖 200 MiB 文件和 multipart 开销，超时覆盖慢速上传。
4. 预览响应与鉴权不被 CDN/入口缓存；不移除预览 Cookie，不缓存 401/403 后回放内容。
5. 正式内容遵守 ETag/no-cache，不自行生成 Last-Modified 或忽略 Range/HEAD 状态。
6. 暂停后，首页、已知资源、HEAD、Range 和条件请求均被阻断；恢复不复活原预览授权。
7. 现有 `douyacn.com` 应用的 Domain Cookie 和同站请求防护需单独核查。当前无法仅凭域名判断其他业务是否安全隔离。

公开入口带宽、并发与滥用限流由现有网关实施。本版 Caddy 使用官方标准镜像，未打包开发设计中的额外限流模块。

后台登录经代理时，设置 `DROP_TRUSTED_PROXY_CIDRS` 为 app 实际看到的直接入口对端 IP 或最小范围 CIDR；Docker NAT 下它可能不同于宿主机入口监听地址。入口须追加真实客户端地址，或覆盖客户端传入的 X-Forwarded-For。应用只在直接对端可信时处理转发链，从右向左跳过可信代理，到第一个非可信地址停止；所解析的链异常时回退到直接对端。多个同名头按收到的顺序合并。不要信任所有地址，配置会拒绝 `0.0.0.0/0` 和 `::/0`。

每客户端仍限制每分钟 10 次，应用全局限制每分钟 30 次。可信转发可避免所有浏览器共享代理的单 IP 限额；全局资源上限仍可能被访问者耗尽，须结合管理入口的访问范围和外层限流验收登录可用性。

## 4. 存储与日常维护

### 4.1 状态核对与回收

`drop_data` 卷中包含 `uploads/`、`quarantine/`、`releases/`、`runtime/`。不可变版本目录为 `releases/<deploymentId>/public/`，同级 `manifest.json` 记录文件清单和 SHA-256。每个公开文件旁有 `.drop-etag` sidecar，网关禁止直接访问它。

`READY` 仅表示文件已验证并持久化。发布协调器记录持久化意图，对候选内容先探测，再使用 Caddy ETag/If-Match 切换，回读路由并校验内容，最后标记 `APPLIED`。接口返回 202 后应继续查询 Publication，不把 HTTP 202 当作发布成功。

暂停已应用或已接受为期望状态时，发布和回滚均返回 `SITE_PAUSED`，自动发布也受同一规则约束。必须由具备 `sites:manage` 的身份显式恢复；上传检查完成不会恢复公开访问。

普通恢复继续使用已应用且可用的版本。没有旧正式版本，或旧产物已不可用时，可在暂停站点的 READY 历史版本上选择“以此版本恢复服务”，确认报告与警告后恢复到该版本。自动化对应 `POST /api/v1/sites/{siteId}/resume`：传入当前 `expectedGeneration`，选择替代版本时另传 `deploymentId`、`inspectionReportHash`、`acknowledgeWarnings`。目标必须属于该站点且 READY/AVAILABLE；返回 Publication 后仍须等待 APPLIED。仅具备 `publications:write` 的 Token 不能调用此恢复操作。

请求 `publishAfterReady` 的 Deployment 另有 `autoPublicationId`、`autoPublishErrorCode`、`autoPublishErrorMessage`。前者表示发布意图已被接受，仍需查询其 Publication 至 APPLIED；后两者记录代次冲突、暂停、Token 撤销/权限不足或未确认警告等拒绝原因。文件仍保持 READY。暂时的数据库或结果保存失败会继续重试，不被当作文件处理失败。

升级会关联有可靠自动发布幂等记录的历史 Publication；旧版已结束处理的 READY 自动发布请求若无法可靠关联结果，则记录 `AUTO_PUBLISH_OUTCOME_UNKNOWN`，保持 READY 且不自动新建发布。操作者须先核对已有 Publication 与正式响应，确认需要切换后再显式发布；历史结果不能全部重建。

```bash
docker compose exec -T app drop-entrypoint drop doctor
docker compose exec -T app drop-entrypoint drop gc --dry-run
```

`doctor` 验证数据库连接、正式站点路由代次、当前文件校验、正文与 ETag；检测到待处理意图或漂移时输出 `pendingPublications` 和 `drift`。存在待处理发布意图，或站点期望状态/版本与已应用状态/版本不一致时，退出码非零；不能仅凭旧正式页面可访问判断暂停或删除已完成。已确认失败的操作也会推进 generation，单独的代次差异不算状态漂移。

GC 默认保留最近 10 个可用版本，回收站默认 7 天。当前/期望正式版本、活跃发布、固定版本、有效预览和导出 pin 会受到保护。标记 GC_PENDING 并确认网关不再引用后才删除磁盘文件；新版本有 120 秒保护期。导出 pin 在请求返回时删除，30 分钟到期为异常中断或清理失败的兜底。

失败和取消的原始上传在 24 小时后进入清理条件；后台每分钟维护一次。终态至少稳定 150 秒且无 PENDING/RUNNING PROCESS 任务后，维护在 GC/配额锁和状态复核下测量上传目录、对应 quarantine 暂存树和未可用 release 树，将最坏情况预留缩至保守的实际保留量。计量取逻辑大小与已分配块的较大值，并增加文件/目录元数据余量；仍有文件不释放配额。链接、特殊文件、扫描失败或锁被占用时保留原预留。

原始上传删除后，其他暂存树仍保留计量；无法安全确认的存储和较长备份仍可能延后预留刷新，系统页可查看。缩短版本保留策略涉及批量回收，本版设置 API 只允许延长，界面没有立即缩短的入口。

### 4.2 未知发布状态的核验与恢复

`APPLYING` 或 `RECOVERING` 表示公开路由尚未核实。协调器保持全局切换、版本回收和备份阻断，因为补偿可能恢复整个网关快照；并行修改其他站点可能被快照覆盖。已接受的暂停/删除会立即撤销预览，但正式路径仍须以对应 Publication 的 `APPLIED` 与实际响应为准。

自动恢复也验证完整目标配置、全部活跃产物完整性和每个站点的正文/ETag 或禁用响应，并在提交前再次回读配置；补偿核验完整已应用基线后才记录失败。仅目标站点正常不能证明其他站点和网关配置一致。

先核对应用日志、数据库和 Caddy 连通性，再读取目标发布的状态与网关配置哈希：

```bash
docker compose exec -T app drop-entrypoint drop reconcile "<publication-id>"
```

未指定 `--mode` 时只读，不验证文件或公开正文。JSON 包含 `publicationId`、`status`、`mode`、`operatorMode`、目标 `action`/`targetStatus`/`targetGeneration`/`deploymentId`、`gatewayConfigHash`、`targetConfigMatches`、`appliedConfigMatches`、`pendingPublications`、`drift` 和 `verifiedSites`。两个匹配布尔值仅比较完整配置；其中漂移记录描述站点已应用和期望的状态、版本、代次，输出不包含完整网关配置或内部凭据。inspect 的 `verifiedSites` 为 0，写入模式完成逐站点验证后才报告其验证数。

根据目标操作和配置匹配情况决定：`targetConfigMatches=true` 时可选择 complete 核验目标；需要恢复数据库已应用基线时选择 restore-applied。配置匹配本身不能代替文件与正文核验。使用刚才的 `gatewayConfigHash` 执行相应操作，选项必须写在 publication ID 之前：

```bash
# 仅当当前网关已是该发布的完整目标配置时，完成核验并确认应用。
docker compose exec -T app drop-entrypoint drop reconcile \
  --mode complete --expected-config-hash "<gatewayConfigHash>" "<publication-id>"

# 重建数据库中已应用的基线配置，核验后恢复该基线。
docker compose exec -T app drop-entrypoint drop reconcile \
  --mode restore-applied --expected-config-hash "<gatewayConfigHash>" "<publication-id>"

docker compose exec -T app drop-entrypoint drop doctor
```

`complete` 要求网关完整配置匹配目标，产物校验通过，所有相关站点的正文与 ETag 或禁用响应通过；已标记必须补偿的发布不能直接完成。`restore-applied` 根据数据库已应用状态构建基线，即使缺少 `previous_config` 也可尝试；应用前先校验产物，通过 Caddy If-Match 写入后回读完整配置并验证所有站点，全部通过才将目标发布标为 FAILED、重置其期望状态并结束对应任务。

两个写入模式都校验操作者读取的配置哈希；网关已变化时拒绝执行，须重新检查。核验过程串行取得发布协调、接受意图和 GC 锁；锁被占用时返回忙状态。无法证明配置、文件或响应时保留 RECOVERING 和全局阻断。其他待处理 Publication 不会被清除，待其正常完成后再要求 doctor 全部通过。不要直接修改数据库状态、删除恢复行或手工解锁来跳过核验。

写入决策持久化为 `operatorMode`，核验未完成时后台任务保持阻断，不会继续推进原目标或撤销操作者的恢复决定。complete 无法核实时，可在重新 inspect、取得新配置哈希后显式选择 restore-applied；已选择 restore-applied 后不能反向改为 complete。完整核验并提交后才清除标记。单次命令最长运行 10 分钟；服务数据库连接池至少需要两个连接，默认配置高于此要求。

## 5. 备份

设置一个独立的 Restic 仓库。`.secrets/restic.key` 是解密材料，应另行保管；仓库丢失或口令丢失均不能恢复数据。先用本地卷做恢复演练时可设置 `RESTIC_REPOSITORY=/backup-repository`，但同机卷不提供主机损坏防护。

```bash
# .env 中配置 RESTIC_REPOSITORY 后重新应用容器环境。
docker compose up -d

# 仅对尚未初始化的新 Restic 仓库执行一次。
docker compose exec -T app drop-entrypoint restic init

# 创建一致备份并读取校验仓库数据。
docker compose exec -T app drop-entrypoint drop backup
```

备份流程：取得发布/GC 协调锁，拒绝未知网关状态；导出 PostgreSQL repeatable-read snapshot，使用 `pg_dump --snapshot` 保存匹配数据库；保存当时网关配置和内部密钥；在 GC 锁保护下校验并硬链接此快照引用的不可变产物；加密写入 Restic；执行 `restic check --read-data`，成功后更新备份记录。数据库导出后释放发布锁，GC 锁保留到备份结束。

完整仓库读取校验期间旧正式版本回收与失败上传的保守预留刷新会延后；24 小时上传目录清理不使用该 GC 锁，但清理后只有完整残留计量通过才释放相应预留。备份时应监控实际存储容量，分别查看保留文件和暂未刷新的预留。

快照包括 `database.dump`、`gateway.json`、`credentials.json`、`backup-manifest.json` 和 `releases/`。正在传输、等待检查或等待用户选择的临时上传不包含在备份中；恢复后会标为失败并要求重新上传。

当前没有内置定时器。运维可在主机调度上述备份命令，观察退出码并检查备份时间。远端仓库鉴权（如 S3 的访问配置）由部署环境注入，不能写进 `.env.example` 或仓库。

## 6. 恢复

恢复脚本要求显式 snapshot ID 和**不存在的目标目录**，可选数据库必须为空。它不会覆盖运行中的站点目录或自动替换网关。

准备 Python 3、Restic、PostgreSQL 16 客户端。使用新的 PostgreSQL 数据库和新的存储目录进行恢复演练：

```bash
export RESTIC_REPOSITORY=/path/to/repository
export RESTIC_PASSWORD_FILE=/safe/path/restic.key
restic snapshots

# /safe/path/restore-db.url 存放新建空库的连接 URL，不在命令行暴露密码。
python3 scripts/restore.py <snapshot-id> \
  --target /safe/path/drop-restored \
  --database-url-file /safe/path/restore-db.url
```

脚本执行 Restic 恢复及校验，逐文件检查清单 SHA-256 和大小，再向空库执行 `pg_restore --single-transaction`。恢复时清除管理员会话、预览会话和临时 pin，撤销预览授权，取消尚未生效的任务，保持已生效版本与路由代次。

将验证后的内容接入一套**新的** Compose 项目或恢复主机：

1. 将 `releases/` 放入新数据卷的相同子路径；创建空的 `uploads/`、`quarantine/`、`runtime/` 并设为 UID/GID 10001。
2. 使用恢复后的数据库和新库密码；从 `credentials.json` 取出内部密钥、worker 密钥写入新的受保护 secret 文件。管理员密码哈希已在数据库中；忘记密码可执行下述维护命令。
3. 将 `gateway.json` 放入新 Caddy 配置卷的 `/config/caddy/autosave.json`。保持内部服务名称和产物路径一致，Caddy 启动使用 `--resume`。
4. 核对管理/内容域名及新入口路由，运行 `drop doctor`。对至少一个当前版本和一个历史版本验证 GET/HEAD/Range、ETag、回滚、暂停以及预览重新授权。
5. 验证完成后才将正式入口指向恢复环境。旧数据保留至人工确认恢复结果。

密码重置从标准输入读取，不将密码放入命令参数：

```bash
# 密码文件由操作者在受保护位置准备，命令执行后所有管理会话失效。
docker compose exec -T app drop-entrypoint drop reset-password < /safe/path/new-password
```

同机恢复演练验证软件流程；真实异机恢复、目标磁盘吞吐和实际 RTO/RPO 仍需在生产设施上验收。

## 7. 升级与排障

先做已验证备份，再更新代码并构建新镜像。数据库迁移带版本表和事务，应用启动时按序执行。不要在未检查 schema 兼容性时简单回退旧二进制；涉及不兼容 schema 的回退需使用备份恢复方案。

```bash
docker compose exec -T app drop-entrypoint drop backup
docker compose up -d --build
docker compose exec -T app drop-entrypoint drop doctor
```

| 现象 | 检查和处理 |
|---|---|
| `ORIGIN_REJECTED` 或后台 404 | `DROP_ADMIN_ORIGIN` 与浏览器地址、端口、Host/Origin 转发是否完全一致 |
| 登录成功但内容未发布 | 检查 Deployment 是否 READY、Publication 是否 APPLIED；新建站点与检查本身不会切换路由 |
| `RECOVERING` | 查看日志与 Caddy 连通性；按 4.2 节先 inspect，再以配置哈希核验 complete 或 restore-applied；无法核实时继续阻断 |
| doctor 输出 `pendingPublications` 或 `drift` | 发布意图尚未完成或期望/已应用状态不一致；先查 Publication，确认正式响应，不把旧路由通过当作最新意图成功 |
| `QUOTA_EXCEEDED` | 查看系统页预留与已用空间；失败上传仍有暂存期，固定/预览版本不会被提前回收 |
| `STORAGE_LOW` | 检查宿主机及 Docker 虚拟磁盘可用空间、inode 和数据卷位置 |
| 预览返回 401/403 | 检查是否兑换过一次性链接、是否过期/撤销、站点是否暂停；创建新授权 |
| 预览返回 502/503 | 鉴权后端或数据库不可用；正式内容可独立工作，预览拒绝访问 |
| Docker 拉取失败 | 检查 Docker daemon 的网络和镜像源；不要关闭应用鉴权或沙箱绕过网络错误 |
| `permission denied` 读取产物 | 检查卷中文件的 UID/GID 和 worker/Caddy 的挂载子目录，不要改为全盘可写 |

日志使用 requestId、deploymentId、publicationId 定位，不记录 Bearer Token、会话 Cookie 或预览一次性密钥。导出、备份和数据库转储仍含用户内容，遵循实际数据保管要求。
